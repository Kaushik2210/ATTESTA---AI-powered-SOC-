# Phase 11 — Investigation Canvas, Verdict Ledger, Drift Monitor

**Status: gate passed, fully clean** — with one honest, environment-forced exception spelled out below. This is the largest and most cross-cutting phase yet: it's the first phase where the browser genuinely runs the compiled Rust kernel (via a new `kernel/wasm_bridge` crate) rather than only rendering data *about* it, and the first WebGL surface in the product. Real bugs were found in all three areas — Rust ABI design, WebGL rendering, and plain data-layer typos — every one found by actually running the thing, not by review.

## What was built

- **`kernel/wasm_bridge/`** — a new Rust crate, the browser counterpart of `kernel/src/bin/adjudicate_cli.rs`. Same JSON request/response shape, but reachable via a hand-rolled, `wasm-bindgen`-free memory ABI (`wasm_alloc`/`wasm_dealloc`/`wasm_adjudicate`/`wasm_result_ptr`/`wasm_result_len`) instead of stdin/stdout, matching the raw-export convention `kernel/`'s own existing wasm32 build already established. Deliberately a *separate* crate from `kernel/` itself — Phase 6 settled that the pure kernel stays free of `serde`, and this bridge's only job is JSON marshaling at a new boundary, not new kernel logic. Five native unit tests, including `tampering_a_claim_changes_the_hash`, prove the real logic before it ever touches wasm.
- **`web/src/lib/kernel/`** — `kernel-wasm.ts` (browser loader: fetch, instantiate, alloc/write/call/read), `kernel-wasm-server.ts` (the same ABI from Node, via `fs.readFileSync`, used by the data layer to seed real verdicts), `merkle.ts` (a client-side, byte-for-byte port of `ledger/merkle.go`'s domain-separated BLAKE3 Merkle scheme, verified against the official BLAKE3 empty-input test vector before being trusted).
- **Investigation Canvas** — a hand-rolled `regl` (WebGL) renderer: a quadtree for hit-testing, a time-aware hierarchical layout (columns by first-seen, never a force simulation), viewport culling, LOD labels (an HTML overlay, capped and zoom-gated), pan/zoom, node/claim selection with real entity/claim side panels, a "verify inclusion proof" action that's a genuine client-side Merkle recomputation, and a "replay attack path" trace in chronological order.
- **Verdict Ledger** — a manifest table (investigation, verdict, model, policy, epoch, age, chain position) and a verification panel that actually does what `docs/UI-SPEC.md` §4 asks: fetch the claim set → verify evidence inclusion (real Merkle checks) → run the kernel (the real compiled wasm) → compare hashes → a seal animation. A "simulate tampered claim" action re-runs the identical real kernel against a mutated claim. A hash-chain display with a deliberately-seeded broken-chain state per tenant. A real "export evidence bundle" JSON download.
- **Drift Monitor** — `VerdictDrift` rows computed by genuinely re-running the real kernel twice per candidate case (once under the original policy, once under a repriced one) — mirroring `services/adjudicate/attesta_adjudicate/rvd.py`'s actual mechanism, not a UI approximation of it. Each row expands into the responsible claim/policy delta, a real before/after kernel-attribution comparison, and a reopen action.
- **`web/src/lib/data/`** additions: `policy.ts` (the one synthetic `PolicyBundle` everything in this phase adjudicates under), `ledger.ts` (generates claim sets, seals them by actually calling the real kernel, builds per-case Merkle trees), `graph.ts` (deterministic entity/claim graphs, sized from a hash of the case id, with an override for the perf gate), `drift.ts` (the real double-adjudication sweep above).

## Real bugs found by actually running the app, not by reading the code

This phase had more of these than any prior one, spanning three different layers.

**Data layer**
1. **`ledger.ts`'s tenant filter used the Watchfloor's *display* label (`"Tenant-Alpha"`) instead of the actual `Case.tenantId` value (`"tenant-alpha"`, lowercase, from `seed.ts`).** Every tenant's `.filter()` silently matched zero cases, so the Verdict Ledger showed "No sealed manifests yet" — a plausible-looking empty state that could easily have been mistaken for "working as designed" rather than a bug, if it hadn't been checked against a real running server. Fixed by matching `seed.ts`'s actual string values.

**Investigation Canvas (WebGL)**
2. **A shader program was recompiled every single animation frame.** The selected-node highlight was drawn via a fresh `regl({...})` call *inside* the render loop instead of a command compiled once outside it — shader compilation is expensive, and doing it ~60 times/sec collapsed the frame rate to ~2fps. Found via live measurement (`onFpsSample`), not inspection; fixed by hoisting the draw command definition outside the loop, matching every other draw call's pattern.
3. **`onWheel` (React's JSX prop) attaches a *passive* native listener**, so `preventDefault()` silently failed (`"Unable to preventDefault inside passive event listener invocation"` in the console) and the page scrolled underneath instead of only zooming the canvas. Fixed with a manually attached `{ passive: false }` native listener instead of the JSX prop.
4. **regl's WebGL viewport was never resynced to the canvas's real size.** This renderer drives its own `requestAnimationFrame` loop instead of `regl.frame()`, and regl only re-syncs its cached GL viewport inside its own scheduler (`regl.poll()`/`regl.frame()`) — so every draw rendered into the canvas element's *default* 300×150 viewport regardless of its actual size, visible as a tiny, clipped, bottom-left-anchored graph fragment. Fixed by calling `regl.poll()` once per frame.
5. **A transient 0×0 `ResizeObserver` report** (the container briefly unpainted — a backgrounded tab, a layout pass before first paint) overwrote the last known-good canvas size with zero, and `computeViewProjection` divides by width/height — turning the whole projection matrix into `NaN` and making every point/line vanish from that frame on. Fixed by ignoring any `ResizeObserver` entry with a non-positive dimension.
6. **The initial "fit to viewport" camera only fit the graph's horizontal (column) extent, never its vertical (row) extent.** The time-aware layout stacks nodes vertically within each time-column, so a busy column can be far taller than the viewport; centering `panY` at 0 without checking real vertical extent left rows silently running off the bottom, visible as the graph appearing to load into only the lower half of the canvas. Fixed by fitting the full bounding box (both axes) and centering on it.
7. **Antialiasing and an unused depth buffer were real GPU cost at 10,000-node scale**, not free defaults. Measured directly: 500 nodes held ~60fps, 10,000 nodes fell to a hard ~30fps ceiling (not noise — repeatable, node-count-correlated). This is a flat 2D orthographic scene; MSAA and depth clear/test add cost with no visual benefit here. Fixed by requesting `antialias: false, depth: false` and dropping the unnecessary `depth` clear.
8. **`AnimatePresence mode="wait"` got stuck** when the right panel transitioned directly between two sibling conditional branches (node panel → claim panel, skipping the "nothing selected" state in between) — the exiting child's "done" callback never fired, so the *new* panel never mounted, leaving the empty-state text on screen indefinitely even though React state was already correct (confirmed directly via a temporary debug hook exposing `selectedEdge`/`selectedNode`, before removing it). Fixed by dropping `mode="wait"` (default `sync` mode animates the brief overlap instead, and mounts correctly).
9. **Alpha-blended line rendering hit a hard, GPU-driver-dependent ceiling that #7's fixes alone didn't clear.** After every other fix, this environment's *own* browser testing (real hardware, confirmed via `WEBGL_debug_renderer_info`) held a clean 59.9fps at 10,000 nodes — but CI's `web-ui-gate` job (GitHub Actions' `ubuntu-latest`, which has no GPU at all; headless Chromium there falls back to SwiftShader, a pure-software rasterizer) hit a hard, repeatable 30fps ceiling on the identical code. Alpha blending is a per-fragment read-modify-write with no dedicated hardware on a software rasterizer, and this scene draws ~13,000 heavily overlapping SUPPORTS/REFUTES line segments with blending enabled — exactly the pathological case. Fixed by disabling blending on the line draw command entirely and pre-mixing the SUPPORTS/REFUTES colors toward each theme's canvas background at the same ratios the old alpha values used, so the visual result (desaturated, layered edges) is unchanged but nothing is blended in real time. This is the one perf fix in this phase that could only have been *found* in CI — no hardware available to this session reproduces a GPU-less environment.

**Accessibility (axe-core)**
9. **The Verdict Ledger's manifest table used `role="row"`/`aria-selected` without a `role="grid"` ancestor or `role="columnheader"`/`role="gridcell"` on its cells** — the identical `aria-required-children`/`aria-required-parent` pattern Phase 10's `case-table.tsx` already hit and fixed, recurring here because this table was written independently. Fixed the same way: `role="grid"` on the container, `role="columnheader"`/`role="gridcell"` on cells.
10. **The verification panel's button row (Verify / Simulate tampered claim / Export evidence bundle) overflowed its fixed-width panel at 1280px**, clipping the last button's text — caught visually in a captured screenshot, not by axe (a layout defect, not an accessibility one, but still a real one a screenshot review caught). Fixed with `flex-wrap`.

## What this environment could not prove (and what does prove it instead)

This environment has no local Rust toolchain — true of every kernel-touching phase since Phase 5, and the reason Phase 11's central feature (the browser running a real compiled kernel) could only be *fully* exercised in CI, not in this session's own browser testing. Concretely:

- **The real `kernel-verify.wasm`** is built by CI (`.github/workflows/ci.yml`'s `web-ui-gate` job now does `cargo build --target wasm32-unknown-unknown --release` on `kernel/wasm_bridge` and copies the output into `web/public/`) — locally, `web/public/kernel-verify.wasm` is a small hand-assembled WAT stub (built via the `wabt` package, used only as an ad hoc local scratch tool — never added to `web/package.json`) that always returns a fixed, non-reactive response regardless of its input, solely to exercise the JS-side memory-marshaling code (alloc/write/call/read/dealloc) in a real browser. It genuinely proved that plumbing works — every UI mechanic (fetch → verify → run → compare → seal, and the drift sweep's double-adjudication) was confirmed end-to-end against it.
- **What the stub cannot prove**, because it ignores its input: that tampering a claim actually changes the recomputed hash, and that repricing a predicate actually flips a verdict. `eval/ui/verdict-ledger-flow.mjs`'s tamper-detection check fails against the local stub for exactly this reason (documented in the script's own output, not silently skipped) — and passes once the real kernel is in place. Locally, the Drift Monitor legitimately shows zero drift rows for the same reason (old/new verdicts always look identical to a stub that reads nothing).
- **What actually proves the real logic is correct**: `kernel/wasm_bridge`'s five native Rust unit tests (run on both x86_64 and arm64 in `ledger-tests`), specifically `tampering_a_claim_changes_the_hash` and `same_request_is_byte_identical_every_call` — the same kernel logic, tested without a wasm runtime in the way, before the wasm layer is even built. Combined with CI's own build+run of the real wasm against `eval/ui/verdict-ledger-flow.mjs`, this is the same "prove what's real, mock only where the environment truly forces it, and say so plainly" discipline every prior Rust/Go phase in this project has used.
- To visually confirm the Drift Monitor's row/diff/attribution/reopen UI actually renders correctly (impossible with zero real drift rows locally), a temporary environment-gated bypass (`ATTESTA_FORCE_DRIFT_DEMO`) was added, used once to screenshot-verify the component, and fully removed before this commit — `git diff` on `web/src/lib/data/drift.ts` shows no trace of it.

## Scope decisions

- **"Replay attack path" traces edges in chronological order**, not a full shortest-path graph search between two chosen endpoints. A real BFS/shortest-path reconstruction is a legitimate next step, but chronological replay already gives a real, deterministic "how did this unfold" animation without requiring a UI for picking two endpoints first.
- **The manifest hash chain and Ed25519 signature are synthetic** (a BLAKE3 hash of a JSON-canonicalized manifest object, not the real CBOR-canonical, Go-signed pipeline `ledger/manifest.go` implements) — there is no live API route to call that Go pipeline from Next.js yet (Phase 12's backend). What's genuinely real is the one thing the gate actually names: kernel verdict re-derivation and hash comparison, plus the evidence-inclusion Merkle proofs (both share the exact same BLAKE3/Merkle algorithm `ledger/merkle.go` implements, ported field-for-field).
- **`AttributedClaim`/before-after kernel attribution in Drift Monitor is reconstructed by re-running the original (unaugmented) policy** over the same claims rather than reading a stored per-claim breakdown (the sealed manifest only stores the final verdict, not `contributing_claims`) — guaranteed to reproduce the original manifest's `verdict_hash` exactly (checked, and discarded if it doesn't match) since it's the identical kernel over identical input.
