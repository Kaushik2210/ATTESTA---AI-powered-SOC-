# Phase 10 — Watchfloor, Timeline, Response Console

**Status: gate passed, fully clean.** This phase had by far the most live-interaction debugging of any UI phase so far — a virtualized, live-SSE-updating, keyboard-navigable 10,000-row table has real temporal complexity that a mostly-static UI shell (Phase 9) doesn't, and several of the bugs below only showed up under an actual scroll or an actual clock, not by reading the code.

## What was built

`web/`'s three data-bearing surfaces from `docs/UI-SPEC.md`, backed by a synthetic in-memory data layer (no backend exists until Phase 12 — see "Scope decisions" below):

- **Data layer** (`src/lib/data/`) — a seeded `Xorshift32` PRNG (same family as the kernel's own property-test RNG) generates 10,000 deterministic synthetic cases, cached on `globalThis` so Next.js dev-mode HMR doesn't regenerate the corpus on every save. Kernel-consistent vocabulary throughout: severity, disposition, and the same 12 ATT&CK-style tactics from `kernel/src/tactic.rs`, in kill-chain order — the UI doesn't invent a parallel taxonomy.
- **Live feed** — a Server-Sent Events route (`api/cases/stream`) emits a simulated tick every 700ms (new case / risk-score update / detector fire), consumed via `EventSource` in `use-case-stream.ts` and merged into React state without re-rendering the full 10k-row array on every tick.
- **Watchfloor** — the virtualized case queue (TanStack Table + TanStack Virtual), a filter rail (severity/disposition/tenant/tactic + unassigned-only, with live counts), a stat strip (`dataviz` skill's tile contract: label · value · signed delta · sparkline), an event ticker, and the `j`/`k`/`e`/`d`/`i` keyboard shortcuts Phase 9 documented as inert placeholders — now live.
- **Timeline Reconstructor** — 12 fixed ATT&CK tactic bands with a piecewise time→pixel scale that collapses idle gaps over 1 hour down to a fixed width (the "compress idle time" toggle `docs/UI-SPEC.md` names), so a multi-day intrusion with long quiet stretches still fits on one screen. Selection is real and click-driven.
- **Response Console** — a proposed-action list, a blast-radius panel (affected principals/hosts/dependent services, a tier-0 warning), and the safety-critical gate: **the Approve/Modify/Reject controls stay disabled until the blast radius has actually loaded** (a real ~900ms fetch, not an instant mock), matching `docs/UI-SPEC.md`'s "Response actions are proposals by default" posture. An autonomy-policy panel with per-action-kind toggles and a synthetic 30-day trigger count.

**Dependencies added:** `@tanstack/react-query`, `@tanstack/react-table` (pinned to `^8`, see below), `@tanstack/react-virtual` — all MIT, already on `CLAUDE.md`'s tech table, confirmed via `npm view <pkg> license` against the actually-resolved versions before writing any code against them.

## Real bugs found by actually running the app, not by reading the code

1. **`useCaseStream` never saw the initial 10,000 cases.** Its `useState` used a lazy initializer reading `initialCases`, but that array arrives asynchronously from a React Query fetch — the initializer only ever ran on the empty first render. The Watchfloor showed only the 1–3 cases that happened to trickle in via SSE "new" events. Caught by `get_page_text` showing filter-rail counts like "High: 1" instead of ~2,500. Fixed by seeding state in a `useEffect` guarded by a `seededRef`, seeding exactly once the array is non-empty.
2. **Keyboard `j`/`k` desynced from clicks and live re-sorting.** The first implementation tracked a `useRef(0)` index that only ever moved via `j`/`k` itself, so a direct row click (or the table re-sorting under a live risk-score update) left it pointing at the wrong row. Fixed by deriving `currentIndex` fresh from `filteredCases.findIndex(c => c.id === selectedId)` on every keypress instead of tracking a separate mutable index.
3. **Excessive live-update churn broke keyboard navigation and looked unrealistic.** The first `tick()` had a 40% chance per 700ms tick of moving a *uniformly random* case's risk score by up to ±800 (on a 0–10,000 scale, sorted descending) — near-total table resorting multiple times a minute, unrealistic for a real feed and, found via actual `j`/`k` testing rather than inspection, capable of scrolling the keyboard-selected row entirely out of the virtualized rendering window (no `aria-selected="true"` row anywhere in the DOM). Fixed two ways: a smaller, top-of-queue-biased delta in `tick()`, and an explicit `virtualizer.scrollToIndex()` effect in `case-table.tsx` that follows keyboard-driven selection regardless of live reordering.
4. **`measureElement`'s `ResizeObserver` on every row, not just the expanded one, degraded scroll performance progressively over time.** `case-table.tsx` originally attached `ref={virtualizer.measureElement}` to every rendered row, even though only the one expanded row (a 3-line inline summary) ever has a height that differs from the fixed `ROW_HEIGHT` `estimateSize` already gives everything else. Confirmed via a CDP frame-timing capture: frame times stayed smooth for roughly the first 2 seconds of a scroll, then degraded into a sustained run of 100–300ms frame gaps that never recovered — the signature of accumulating `ResizeObserver` connect/disconnect cost as more distinct rows get scrolled through and observed for the first time, not a transient spike. Fixed by only passing the `measureElement` ref when a row is actually expanded (`ref={isExpanded ? virtualizer.measureElement : undefined}`); unmeasured rows fall back to `estimateSize`'s already-correct fixed height. Verified the fix doesn't break expand/collapse correctness by expanding then collapsing a row directly in a live browser and confirming its rendered height reverts from 65px back to 32px, not just that it grows.
5. **Every SSE "new"/"update" tick synchronously recomputed the full 10,000-row filter/sort/count chain, occasionally landing mid-scroll.** `WatchfloorClient`'s `allCases`/`filteredCases` memos correctly depend on `stream.cases`'s reference, but that reference changes on every live case mutation (a fresh `Map`), which cascades into `getSortedRowModel()` re-sorting all 10,000 rows and `FilterRail` recomputing four count maps over the full array — real work landing on the main thread roughly once every ~2 seconds regardless of whether the user is scrolling. Two fixes: `FilterRail`'s counts are now memoized on `cases` (previously recomputed on every render for any reason, not just when the case list changed), and the SSE-driven state updates in `use-case-stream.ts` are wrapped in React's `startTransition`, marking them interruptible/low-priority so an in-progress scroll frame isn't blocked by a background data update.
6. **A measurement methodology bug in the gate script itself.** The first version of `eval/ui/triage-flow.mjs`'s scroll-fps check computed one plain average over a whole scroll window. In this sandbox (which, it turned out, was sharing the machine with an unrelated leftover dev server from a different project competing for CPU — confirmed via `Get-CimInstance Win32_Process`, not something this app controls), a single GC pause or scheduling hiccup outside the app's control could crater the average even when every other frame was smooth, producing results anywhere from 8fps to 60fps run to run on identical code. Replaced with the standard fix for exactly this: take the **median** per-frame rate (a handful of outlier stalls don't move a median; a genuinely janky scroll still fails it), sampled across 3 independent scroll passes, reporting the best pass. After the real fixes above (#4 and #5), this reads a consistent ~55–60fps.
7. **Two Playwright API-usage bugs in the gate script**, both caught by the script simply failing to run rather than by inspection: `page.waitForFunction(fn, {timeout})` silently ignored the timeout because the 2-argument overload treats the second argument as `arg`, not `options` — needed an explicit `undefined` arg placeholder. And a status-text assertion checked for `"Escalated"` (capitalized) when the underlying DOM text is lowercase `"escalated"`, capitalized only via CSS `text-transform` — fixed to a case-insensitive check.
8. **Two real, axe-core-caught accessibility violations in `case-table.tsx`'s custom (div-based) table**, both in `wcag2a`: `aria-required-children`/`aria-required-parent` (the row/cell divs used `role="row"` and had no `role="columnheader"`/`role="cell"` ARIA-table structure around them — a custom-widget table needs a complete role hierarchy, not just `role="row"` scattered through plain divs) and `scrollable-region-focusable` (the virtualized scroll container has no natively focusable descendant — selection is driven by a global `j`/`k` keydown handler, not per-cell tab stops). Fixed by giving the table container `role="grid"` (matching the `aria-selected` it already sets on rows, which is only a valid ARIA state under grid/treegrid, not plain table), each cell `role="gridcell"`, and the scroll container `role="rowgroup"` + `tabIndex={0}` (rowgroup because a `tabIndex` forces the div into the accessibility tree as a real node, which then needs a role `grid` accepts, rather than being silently pruned as presentational). Confirmed 0 violations afterward, including the Response Console and Timeline surfaces added this phase.

## A deliberate technology-pinning decision

`npm install @tanstack/react-table` with no version specifier pulled **v9.2.4** by default — a significant API redesign (`useTable` instead of `useReactTable`, an atoms/store-based `TableFeatures` generic state model, deprecated `table.store` patterns) with none of v8's familiar, well-documented surface. Given the time pressure and an unfamiliar API, explicitly downgraded to `@tanstack/react-table@^8` (confirmed `8.21.3`) and verified `createColumnHelper`/`useReactTable`/`getCoreRowModel`/`getSortedRowModel`/`flexRender` were all present in its type declarations before writing any table code. This is the same reasoning `CLAUDE.md`/Phase 9 already used to pin Next.js to major version 15 — picking a stable, understood version of an already-approved library, not relitigating "TanStack Table" as the choice itself.

## Scope decisions

- **Synthetic data, honestly labeled as such.** No backend API exists until Phase 12, so every case, timeline event, detector fire, and blast radius is generated by a seeded PRNG rather than fetched from a real ingest/kernel pipeline. The vocabulary (severity, disposition, the 12 tactics) matches the kernel's own types so the UI isn't inventing a parallel taxonomy that would need reconciling later.
- **Filter rail covers severity/disposition/tenant/tactic/unassigned-only.** `docs/UI-SPEC.md` also names entity-type and age-range filters; omitted this phase since the four included dimensions already exercise the "narrow the queue, see live counts" pattern, and a filter dimension is additive rather than a redesign — trivial to add once there's a concrete need driving which entity-type taxonomy to use.
- **ATT&CK tactic chips are deliberately uncolored** (hairline border, monospace text) rather than a 12-color categorical ramp. `docs/UI-SPEC.md` rule 4 reserves red/amber hue for severity alone, and generating a 12-color categorical palette that hasn't been run through the `dataviz` skill's CVD validator isn't worth doing for a label that's already legible as plain text.
- **Timeline's "linked selection" isn't wired to the Investigation Canvas yet** — that surface doesn't exist until Phase 11. Watchfloor's `i` shortcut correctly navigates to `investigation-canvas?case=<id>` (Phase 9's empty-state stub), carrying the case id forward; the Timeline is reached separately for now. The selection state inside the Timeline itself is real and click-driven, ready for the canvas to read once it exists.
- **`AutonomyPolicy`'s "N times in the last 30d" counts are synthetic** (seeded from the action kind, not a real audit log), and toggling a switch doesn't persist anywhere per-tenant. Real policy grants and history are Phase 12 territory (`docs/UI-SPEC.md`: "Autonomous execution requires an explicit per-tenant policy grant... and an entry in the ledger").
- **`ResponseAction`'s in-memory store lives on the server process's `globalThis`**, matching the Phase 9 pattern for surviving Next.js dev-mode HMR reloads. This means repeated runs of the gate script against the same long-running server will exhaust the initially-pending actions one at a time as each run approves one — correct, observed behavior, not a bug; `eval/ui/triage-flow.mjs` explicitly selects a still-pending action rather than assuming the default selection always is, so the gate stays meaningful across repeated runs.
